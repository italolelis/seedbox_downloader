<objective>
Detect missing/deleted Put.io transfers in the download error path, emit warn-level logs, send distinct Discord embed notifications for "transfer removed" vs "files missing" cases, mark transfers as "missing" in DB to prevent re-processing, and clean up partial local files.

Purpose: When Put.io transfers or their files disappear (user manual deletion, Put.io expiry, etc.), the pipeline currently treats these as generic download errors. This phase makes these failures explicit, informative, and non-repeating.

Output: Updated downloader with missing-transfer detection, Discord embed notifications, and DB status tracking.
</objective>

**1. Add sentinel error variables to `internal/dc/putio/client.go`:**

Add two package-level sentinel errors (following the project pattern of `var ErrX = errors.New(...)` from `storage/storage.go`):

```go
var (
    // ErrTransferFilesNotFound indicates the transfer's files were deleted from Put.io
    // but the transfer itself may still exist.
    ErrTransferFilesNotFound = errors.New("transfer files not found on Put.io")

    // ErrTransferNotFound indicates the transfer itself no longer exists on Put.io.
    ErrTransferNotFound = errors.New("transfer not found on Put.io")
)
```

Add `"errors"` to imports.

In `GetTaggedTorrents`, when `c.putioClient.Files.Get(ctx, t.FileID)` fails (line ~94-98), wrap the error with `ErrTransferFilesNotFound` using `fmt.Errorf("...: %w", ErrTransferFilesNotFound)` instead of just logging and continuing. This is the "files missing" case: transfer exists in the list but its FileID content is gone.

In `GrabFile`, when `c.putioClient.Files.URL(ctx, file.ID, false)` fails, check if the error message indicates the file is gone (Put.io returns 404-class errors for deleted files). Wrap with `ErrTransferFilesNotFound`: `fmt.Errorf("file %d no longer available on Put.io: %w", file.ID, ErrTransferFilesNotFound)`.

**Important design note on "transfer removed" vs "files missing" detection (per user decision):**
- "Files missing" (`ErrTransferFilesNotFound`): Transfer appears in Transfers.List but Files.Get/Files.URL fails for its FileID — the content was deleted while the transfer record remained.
- "Transfer removed" (`ErrTransferNotFound`): This case is harder because a removed transfer simply won't appear in `Transfers.List` results, so it's never returned by `GetTaggedTorrents`. The detection point for this is when `DownloadTransfer` receives a transfer with `len(transfer.Files) == 0` AND the transfer was previously claimed (meaning it showed up once with files, was claimed, but by the time download runs the files are gone). For the `GetTaggedTorrents` path: if `t.FileID != 0` but `Files.Get` fails, that's files-missing. If `t.FileID == 0` for a completed transfer (status is available but no FileID), that could indicate the transfer's file was already cleaned but the transfer record persists — this should be logged but is not actionable for download.

For this phase, focus the detection on the `GrabFile` and `GetTaggedTorrents` error paths since that's where the pipeline encounters missing content during actual download attempts (per user decision: "only react when an operation fails").

**2. Add `NotifyEmbed` method to `internal/notifier/discord.go`:**

Add a `NotifyEmbed` method to the `Notifier` interface and implement it on `DiscordNotifier`. Discord webhook embeds use a different JSON payload structure:

```go
// Embed represents a Discord embed message with structured fields.
type Embed struct {
    Title       string       `json:"title"`
    Description string       `json:"description"`
    Color       int          `json:"color"`
    Fields      []EmbedField `json:"fields"`
    Timestamp   string       `json:"timestamp,omitempty"`
}

type EmbedField struct {
    Name   string `json:"name"`
    Value  string `json:"value"`
    Inline bool   `json:"inline,omitempty"`
}
```

Update the `Notifier` interface to include `NotifyEmbed(embed Embed) error`. The implementation sends a JSON payload of the form `{"embeds": [embed]}` to the webhook URL (Discord supports up to 10 embeds per message; we send 1).

Use color `15158332` (0xE74C3C, red) for missing transfer notifications — this creates the colored sidebar the user requested.

**3. Add `OnTransferMissing` channel and detection logic to `internal/downloader/downloader.go`:**

OnTransferMissing chan *transfer.Transfer

Initialize in `NewDownloader` with `make(chan *transfer.Transfer)`, close in `Close()`.

In `DownloadTransfer`, after `d.DownloadFile` returns an error, check if the error wraps `putio.ErrTransferFilesNotFound` using `errors.Is(err, putio.ErrTransferFilesNotFound)`. If so:

The key insight: the `errgroup.WithContext` in `DownloadTransfer` means when one file fails, the context is cancelled for other files in the same transfer. But OTHER transfers in the batch (received via `WatchDownloads` channel) are on separate goroutine iterations and unaffected — this satisfies the "isolate from other transfers" requirement.

In `WatchDownloads`, after `d.DownloadTransfer` returns an error, check `errors.Is(err, putio.ErrTransferFilesNotFound)` again. If it IS a missing-transfer error, emit to `OnTransferMissing` instead of `OnTransferDownloadError` so the notification handler knows to use the embed format. If it's a regular download error, continue using `OnTransferDownloadError` as before.

**Important:** Import `"github.com/italolelis/seedbox_downloader/internal/dc/putio"` in the downloader package. **1. Add `handleTransferMissing` function to `cmd/seedbox_downloader/main.go`:**

Create a new handler function following the pattern of `handleDownloadError`:

```go
func handleTransferMissing(
    ctx context.Context,
    logger *slog.Logger,
    repo storage.DownloadRepository,
    notif notifier.Notifier,
    t *transfer.Transfer,
    missingType string, // "files_missing" or "transfer_removed"
) {
```

Inside:
1. **Update DB status to "missing"**: Call `repo.UpdateTransferStatus(t.ID, "missing")`. This prevents the transfer from being re-claimed on the next polling cycle (the `ClaimTransfer` SQL only claims `pending` or `failed` status — `missing` is excluded). Log error if DB update fails but continue to notification.

2. **Log at warn level** (per user decision): `logger.WarnContext(ctx, "tracked transfer missing from Put.io", "transfer_id", t.ID, "transfer_name", t.Name, "missing_type", missingType)`

3. **Send Discord embed notification** using `notif.NotifyEmbed(...)`:
   - Title: "Transfer Missing" (for files_missing) or "Transfer Removed" (for transfer_removed)
   - Description: Different wording per case:
     - files_missing: "The files for this transfer were deleted from Put.io while download was in progress."
     - transfer_removed: "This transfer was removed from Put.io before download could complete."
   - Color: `15158332` (red, 0xE74C3C)
   - Fields (inline where appropriate):
     - "Transfer Name" → `t.Name`
     - "Transfer ID" → `t.ID`
     - "Status" → "Files Missing" or "Transfer Removed"
   - Timestamp: `time.Now().UTC().Format(time.RFC3339)`

   Handle the nil notifier case (Discord webhook not configured) — check `if notif != nil` before calling. Log warning if notification fails but don't crash.

**2. Wire into `setupNotificationForDownloader`:**

Add a new case in the notification loop's select statement:

```go
case t := <-downloader.OnTransferMissing:
    handleTransferMissing(ctx, logger, repo, notif, t, "files_missing")
```

The `missingType` is "files_missing" as default since that's the primary detection path via GrabFile errors. If we later add "transfer_removed" detection, the type parameter is already in place.

**Important:** The `notif` variable in `setupNotificationForDownloader` may be nil (when `DISCORD_WEBHOOK_URL` is empty). The `handleTransferMissing` function must guard against nil notifier — only call `NotifyEmbed` if notif is not nil. This matches how `handleDownloadError` already calls `notif.Notify(...)` without nil check (which would panic if webhook is empty — but the existing code relies on `DiscordWebhookURL != ""` check inside `Notify`). For safety, add nil check before calling on notif.

Actually, looking more carefully at the existing code: `handleDownloadError` calls `notif.Notify(...)` directly. The `notif` is either `&notifier.DiscordNotifier{...}` or the zero value from `var notif notifier.Notifier` (which is nil for an interface). If nil, calling `.Notify()` would panic. This means the existing code assumes `DISCORD_WEBHOOK_URL` is always set. However, for robustness in our new handler, add a nil guard: `if notif != nil { notif.NotifyEmbed(...) }`. Consider adding the same nil guard to the existing handlers as a bonus fix, but that's out of scope — just protect the new code.
